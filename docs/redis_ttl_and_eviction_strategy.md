# Redis TTL & Memory Eviction Strategy

These are my design notes on setting explicit key expirations and configuring eviction policies so Redis never runs out of memory under high key cardinality.

---

## 1. Problem Statement

If rate limit keys are created without an explicit expiration (TTL = -1), memory usage grows continuously as new users and IP addresses hit the gateway.

Under sustained traffic or scraping attacks with rotating IPs, unmanaged keys will eventually exhaust available RAM, causing out-of-memory errors and crashing the service.

---

## 2. Mandatory TTL Formulas Per Algorithm

Every Redis key generated by RateFortress has an explicit TTL set on creation or refreshed on access:

| Algorithm | Key Structure | TTL Formula | Rationale |
| :--- | :--- | :--- | :--- |
| Fixed Window Counter | `fixed_window:{user}:{window_id}` | `window_seconds + 1` | Automatically purges previous window counters once the active window has rotated. |
| Sliding Window Counter | `swc:{user}:{window_id}` | `2 * window_seconds + 2` | Current counter must persist through the subsequent window to serve as previous window for weighted calculations. |
| Sliding Window Log | `sliding_log:{user}` | `window_seconds + 1` | Sorted set (ZSET) members become irrelevant once older than window length. |
| Token Bucket | `token_bucket:{user}` | `max(3600, 2 * ceil(capacity / refill_rate))` | Keeps idle client state until full capacity is restored plus a 1-hour buffer. |
| Leaky Bucket | `leaky_bucket:{user}` | `max(3600, 2 * ceil(capacity / leak_rate))` | Holds state until the queue has completely leaked to zero plus a 1-hour buffer. |

---

## 3. Redis Eviction Policies

When Redis hits its allocated memory ceiling (maxmemory), it applies an eviction policy:

### Policy Comparison
1. noeviction: Returns OOM errors when memory is full. This breaks INCR and Lua script writes, forcing the API into error states.
2. allkeys-lru: Evicts the least recently used keys across the entire database. If Redis shares space with cached database objects or app config, it can evict persistent records.
3. volatile-lru: Evicts the least recently used keys among those with an expiration set. Because RateFortress sets a TTL on all rate limit keys, this cleanly drops idle keys without touching persistent data.
4. volatile-ttl: Evicts keys with the shortest remaining TTL first. This risks dropping active short-window counters before longer dormant ones.

Recommended Redis configuration (`redis.conf`):
```ini
maxmemory 2gb
maxmemory-policy volatile-lru
maxmemory-samples 5
```

---

## 4. Memory Budget

- Fixed Window and Sliding Window Counter: roughly 80 to 120 bytes per key. 1,000,000 active concurrent users take about 100 MB.
- Token Bucket and Leaky Bucket (Hash): roughly 150 to 220 bytes per key. 1,000,000 active concurrent users take about 180 MB.
- Sliding Window Log (ZSET): roughly 64 bytes per member plus overhead. 1,000,000 users with 50 requests per window take about 3.5 GB.

Token Bucket and Sliding Window Counter give the best balance of low memory footprint and boundary protection.
