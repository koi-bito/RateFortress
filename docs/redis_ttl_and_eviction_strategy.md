# Architecture Decision Record (ADR): Redis TTL & Memory Eviction Strategy

## 1. Context & Problem Statement

In distributed production environments, RateFortress tracks per-client and per-endpoint request quotas across millions of unique identities (IP addresses, API keys, OAuth client IDs).

If rate limit keys are created without explicit expiration (`TTL == -1`), Redis memory consumption grows monotonically with the cardinality of active callers:
$$\text{Memory} = \mathcal{O}(U \times E)$$
where $U$ is total unique callers and $E$ is the number of monitored endpoints. Under sustained traffic or distributed denial-of-service (DDoS) attacks with IP spoofing, unmanaged keys rapidly exhaust available RAM, triggering Out-Of-Memory (OOM) crashes and service outages.

---

## 2. Decision: Mandatory TTL Strategy Per Algorithm

Every Redis key generated by RateFortress is guaranteed to have a deterministic Time-To-Live (TTL) established upon creation or refreshed upon access:

| Algorithm | Key Structure | TTL Formula | Rationale |
| :--- | :--- | :--- | :--- |
| **Fixed Window Counter** | `fixed_window:{user}:{window_id}` | `window_seconds + 1` | Automatically purges previous window counters once the active window has rotated. |
| **Sliding Window Counter** | `swc:{user}:{window_id}` | `2 * window_seconds + 2` | Current counter must persist through the subsequent window to serve as `previous_window` for weighted calculations. |
| **Sliding Window Log** | `sliding_log:{user}` | `window_seconds + 1` | Pruned sorted set (ZSET) members become completely irrelevant once older than `window_seconds`. |
| **Token Bucket** | `token_bucket:{user}` | $\max(3600, 2 \times \lceil \frac{\text{capacity}}{\text{refill\_rate}} \rceil)$ | Ensures idle client state is retained until full capacity is restored plus a 1-hour safety buffer. |
| **Leaky Bucket** | `leaky_bucket:{user}` | $\max(3600, 2 \times \lceil \frac{\text{capacity}}{\text{leak\_rate}} \rceil)$ | Holds state until the bucket queue has completely drained to zero plus a 1-hour safety buffer. |

## 3. Redis `maxmemory-policy` Configuration Analysis

When Redis reaches its allocated RAM limit (`maxmemory`), it enforces an eviction policy:

### Policy Comparison

1. **`noeviction` (Redis Default):**
   - Returns write errors (`OOM command not allowed when used memory > 'maxmemory'`) when memory is full.
   - **Verdict:** ❌ **Dangerous** for rate limiting. An OOM state breaks all subsequent `INCR`, `ZADD`, and Lua hash writes, forcing the API to trip the circuit breaker and run unthrottled.

2. **`allkeys-lru`:**
   - Evicts the least recently used keys out of all keys in the database.
   - **Risk:** If Redis is shared with application cache or persistent configuration keys, `allkeys-lru` may evict critical configuration data.

3. **`volatile-lru` (RateFortress Recommended):**
   - Evicts the least recently used keys among those with an expiration (`expire`) set.
   - **Verdict:** ✅ **Optimal for Shared Redis Clusters.** Since RateFortress sets a TTL on 100% of its rate-limit keys, volatile-lru cleanly recycles dormant client keys under memory pressure without touching persistent system keys.

4. **`volatile-ttl`:**
   - Evicts keys with the shortest remaining TTL first.
   - **Verdict:** ⚠️ Secondary option; can prematurely purge short-window active counters before longer-window dormant ones.

### Recommended Production Redis Configuration (`redis.conf`):
```ini
maxmemory 2gb
maxmemory-policy volatile-lru
maxmemory-samples 5
```

## 4. Empirical Memory Budget at Scale

- **Fixed Window / Sliding Window Counter:** ~80–120 bytes per key.
  - $1,000,000$ active concurrent users $\approx 100 \text{ MB}$.
- **Token / Leaky Bucket (Hash):** ~150–220 bytes per key.
  - $1,000,000$ active concurrent users $\approx 180 \text{ MB}$.
- **Sliding Window Log (ZSET):** ~64 bytes per member + overhead.
  - $1,000,000$ users $\times$ 50 requests/window $\approx 3.5 \text{ GB}$.

**Conclusion:** Token Bucket and Sliding Window Counter provide the most memory-efficient distributed rate limiting for large-scale fleets.
